# Technocore Signalbox RED-GREEN Microtask Checklist

> **For Hermes:** Execute with `subagent-driven-development`; provide each row’s full specification to a fresh implementer, then run specification review followed by quality/security review before the next row touching the same files.

**Goal:** Decompose the 16 release gateways in `2026-08-29-technocore-signalbox-implementation.md` into focused, executable RED→observed-failure→minimal-GREEN cycles.

**Architecture:** The protocol baseline, implementation plan, and client-contract schema remain authoritative. This checklist controls execution granularity only and may not loosen their bounds, add output fields, enable a quarantined write, or move publication earlier.

**Tech stack:** Python 3.12, `unittest`, `uv`, standard-library HTTP/JSON/filesystem primitives, existing `cryptography`, and Textual only after its feasibility gate.

## Execution rule

For every row: (1) add only the named failing test; (2) run the exact target and record the expected assertion/import failure; (3) add the smallest implementation that makes that test pass; (4) re-run that target normally and with `python -O`; (5) run the named regression target; (6) obtain specification PASS, then quality/security APPROVED. Do not commit: the implementation plan forbids a candidate commit before Task 15 authorization.

Command cells use two mechanically expanded forms. Any `named test` phrase means run the fully qualified test in column 2 with `uv run python -m unittest TEST -v` and `uv run python -O -m unittest TEST -v`; qualifiers such as acceptance, synthetic, fresh-wheel, or evidence do not change that expansion. A backticked space-separated module list means run `uv run python -m unittest MODULE... -v` and its `python -O` equivalent. No implementer may substitute discovery, omit the RED run, or infer a different target. Evidence-only and external-action rows run their named local validator normally/optimized against synthetic hostile and valid records before any separately approved real action.

After the focused pair, every row runs the exact normal and optimized module list for its task: Task 0 `tests.test_compatibility_manifest tests.test_cli tests.test_client tests.test_contract`; Task 1 `tests.test_protocol tests.test_transport tests.test_capabilities tests.test_client`; Task 2 `tests.test_cli tests.test_contract tests.test_client_contract tests.test_packaging`; Task 3 `tests.test_application tests.test_cli`; Task 4 `tests.test_rooms_spike tests.test_rooms tests.test_client tests.test_application tests.test_cli tests.test_client_contract`; Task 5 `tests.test_paths tests.test_cache_spike tests.test_cache tests.test_application tests.test_cli`; Task 6 `tests.test_follow tests.test_cache tests.test_client`; Task 7 `tests.test_search tests.test_cache tests.test_application tests.test_cli`; Task 8 `tests.test_operator_journey`; Task 9 `tests.test_tui_spike tests.test_tui tests.test_application`; Task 10 `tests.test_drafts tests.test_application tests.test_cli tests.test_tui`; Task 11 `tests.test_pending tests.test_transaction tests.test_message tests.test_controlled_post_exercise tests.test_client_contract tests.test_capabilities tests.test_paths tests.test_drafts tests.test_client tests.test_cli tests.test_tui`; Task 12, when enabled, `tests.test_event_gate tests.test_events tests.test_event_consumers tests.test_client_contract tests.test_contract tests.test_application tests.test_cli`; Task 13 `tests.test_brand tests.test_docs tests.test_demo tests.test_assets`; Task 14 `tests.test_candidate_materialization tests.test_artifacts tests.test_security tests.test_upgrade tests.test_release_packet tests.test_release_gates tests.test_controlled_post_exercise`; Task 15 `tests.test_publication`. Expand each list as `uv run python -m unittest MODULE... -v` and `uv run python -O -m unittest MODULE... -v`. Cell text after the focused target records extra evidence or a narrower diagnostic; it never replaces this regression pair.

All human, review, authorization, timing, candidate, and publication evidence uses descriptor-read compact sorted UTF-8 JSON plus LF outside every source tree. The operator creates an absolute `EVIDENCE_ROOT` as an owned `0700` regular directory outside the repository and every candidate; the implementation descriptor-anchors it, rejects links, special files, unsafe ancestors, `.`/`..` components, and any root inside the source tree. Before Task 14.4 freezes a candidate hash, records use `$EVIDENCE_ROOT/pre-candidate/{ID}-{kind}.json`, set `candidate_tree_sha256:null`, and bind `subject_sha256` to the exact planning artifact, fixture set, tool, authorization, or review subject. After Task 14.4, records use `$EVIDENCE_ROOT/{candidate_tree_sha256}/{ID}-{kind}.json`, require `candidate_tree_sha256` to equal the directory component, and bind that final candidate or a separately identified artifact/public object. The candidate hash domain is exactly the sorted relative POSIX path, mode, and content bytes in the isolated exported-and-overlaid source root; it excludes `EVIDENCE_ROOT`, build outputs, `.git`, and parent-directory metadata. Candidate materialization rejects an in-tree `.signalbox-evidence` or `signalbox-evidence` entry. Candidate-bound evidence is created only after the candidate hash is final, so it cannot alter the hash it contains. Every record is closed, duplicate-key- and Unicode-scalar-safe, has `schema_version:1`, a row-specific `kind`, `subject_sha256`, `candidate_tree_sha256`, optional distinct `artifact_sha256`, `created_at`, `status`, and `evidence`; local timestamps use the plan's canonical validator. Row-specific tests freeze required evidence keys, enums, bounds, and cross-field truth. Human acceptance requires `status:"accepted"`; review approval requires zero critical and zero important findings; an external action requires an exact prior approval record and an exact readback record. Missing, stale, mismatched, rejected, or unverifiable evidence keeps the gate closed.
